Section 0.1.1 • Day-1 Security Mental Model

1. Why Software Breaks: Trust Boundaries & Broken Invariants

Before looking at bits and bytes, understand the single most important concept in all of cybersecurity: Vulnerabilities are not magic spells. Every vulnerability is a gap between what the programmer assumed in their head and what the machine actually executes.

Real-World Intuition: The Airport Checkpoint vs. The Car Odometer

Imagine a parking garage that charges 1,000 Taka per day and has a 4-digit mechanical counter (0000 to 9999). The owner writes a rule: "If the counter shows 500 Taka or less, open the gate for free."

A normal driver stays 1 day → counter shows 1000 → gate stays closed. A hacker stays 10 days (10 × 1000 = 10,000) → the 4-digit mechanical counter rolls over from 9999 back to 0000! The machine checks 0000 <= 500 and opens the gate for free.

Two terms you will use every day as a security engineer:

  • Trust Boundary: Any line in a system where untrusted data (an HTTP request, a network packet, a multiplayer game packet, a file uploaded by a user, a CLI argument) crosses into trusted code (your C server, database, or OS kernel).
  • Invariant (Security Assumption): A condition the programmer believes is always true after a check passes. For example:
    • Programmer's Invariant: "If I add 16 header bytes to user_length, the result user_length + 16 is ALWAYS larger than user_length."
    • Hardware Reality: Inside a fixed 32-bit register, if user_length = 4,294,967,288 (0xFFFFFFF8), adding 16 rolls the odometer over to 8! The invariant shatters.
Section 0.1.2 • Speaking the Machine's Native Language

2. Bits, Nibbles, Bytes, Hexadecimal & Bitwise Engineering

At the physical hardware layer, RAM and CPU registers only hold voltage states: 0 or 1 (a Bit).

  • 1 Bit: 0 or 1
  • 1 Nibble (4 Bits): 0000 to 1111 (16 possible patterns: 0 to 15) — maps to exactly ONE Hexadecimal digit (0–F)!
  • 1 Byte (8 Bits = 2 Nibbles): 0000 0000 to 1111 1111 (256 possible patterns: 0 to 255) — maps to exactly TWO Hexadecimal digits (0x00–0xFF)!

Why Security Engineers Never Use Decimal for Memory

In decimal, the number 1,000,000 gives you zero visual clue about which bytes sit in RAM. In hexadecimal, 1,000,000 is 0x000F4240—you can immediately see the 4 exact bytes: 00, 0F, 42, and 40!

The 8-4-2-1 Mental Conversion Trick: Within any 4-bit nibble, the 4 bit positions have weights 8, 4, 2, 1. Just add the weights where a 1 appears:

  • 1010 = 8 + 0 + 2 + 0 = 10 = 0xA
  • 1100 = 8 + 4 + 0 + 0 = 12 = 0xC
  • 1111 = 8 + 4 + 2 + 1 = 15 = 0xF
  • Therefore, byte 1010 1111 = 0xAF! No calculator needed.

Section 0.1.3 • How Hardware Stores Negative Numbers

3. Two's Complement: Step-by-Step Intuition (No Magic)

How do you store -5 in a CPU register when hardware only has 0s and 1s? Early computer designers tried making the leftmost bit (Most Significant Bit, or MSB) a simple sign flag (0000 0101 = +5, 1000 0101 = -5). That failed miserably because adding +5 and -5 with normal binary addition did not give 0, and there were two different zeros (+0 and -0).

Modern CPUs solve this with Two's Complement. Here are the two complementary ways to understand it completely:

Mental Model A — The Negative-Weight MSB Rule (Fastest Way to Read Binary!)

In an unsigned 8-bit integer (uint8_t), the 8 bit weights are all positive:
+128, +64, +32, +16, +8, +4, +2, +1.

In a signed 8-bit integer (int8_t), the leftmost bit (MSB) has a NEGATIVE weight of -128, while the other 7 bits keep their positive weights:
-128, +64, +32, +16, +8, +4, +2, +1!
Let's test this on 1111 1011 (0xFB):
• As uint8_t: 128 + 64 + 32 + 16 + 8 + 0 + 2 + 1 = 251.
• As int8_t: -128 + 64 + 32 + 16 + 8 + 0 + 2 + 1 = -128 + 123 = -5!

Mental Model B — How to Negate Any Number (~x + 1)

Want to find the 8-bit Two's Complement of -5 from +5?
1. Write +5 in 8-bit binary: 0000 0101 (0x05)
2. Invert all bits (~5): 1111 1010 (0xFA)
3. Add 1: 1111 1011 (0xFB)
Check what happens when the CPU adds +5 and -5: 0000 0101 + 1111 1011 = 1 0000 0000. The 9th carry bit falls off the 8-bit register, leaving 0000 0000 (0)! One simple circuit handles both addition and subtraction.

8-Bit Binary Hex As uint8_t (Unsigned) As int8_t (Signed Two's Complement)
0000 0000 0x00 0 0
0000 0001 0x01 1 +1
0111 1111 0x7F 127 +127 (INT8_MAX — largest positive int8_t)
1000 0000 0x80 128 -128 (INT8_MIN — notice +127 + 1 wraps to -128!)
1111 1011 0xFB 251 -5 (-128 + 123 = -5)
1111 1111 0xFF 255 (UINT8_MAX) -1 (all bits 1 is ALWAYS -1 in any signed bit-width!)
Figure 1: Fixed-width arithmetic wraps around mod 2^N—turning large positive sizes into tiny buffers or negative numbers.
Section 0.1.4 • From Bit Math to Critical Exploits

4. The 3 Deadly Integer Vulnerability Classes (Walked Through Line-by-Line)

Vulnerability Class 1: Unsigned Addition / Multiplication Wrap-Around

Real-World Context: Image decoders, video parsers (like Android Stagefright), SSH/network packet parsers, and game servers frequently calculate a buffer size by multiplying item_count * item_size or adding payload_len + header_size. 

/* Vulnerable C Packet / Image Parser */
void parse_image_table(uint32_t num_entries, char *network_data) {
    // Each entry needs 1000 bytes. Max 32-bit uint is 4,294,967,295.
    // What if attacker sends num_entries = 8,589,935?
    // True math: 8,589,935 * 1000 = 8,589,935,000
    // Modulo 2^32 (8,589,935,000 - 2 * 4,294,967,296) = 408 bytes!
    uint32_t total_bytes = num_entries * 1000;   // Wraps around to 408!

    char *table = malloc(total_bytes);           // Allocates a tiny 408-byte heap buffer!
    for (uint32_t i = 0; i < num_entries; i++) {
        memcpy(table + (i * 1000), network_data, 1000); // Writes 8.5 GB past the 408-byte buffer!
    }
}

Vulnerability Class 2: Signed-to-Unsigned Implicit Promotion Trap

Why It Happens: Many C developers declare lengths as int (which is signed!) out of habit, while standard library memory functions like memcpy(void *dst, const void *src, size_t n) and read(int fd, void *buf, size_t count) take size_t (which is an UNSIGNED 64-bit integer on 64-bit Linux!). 

int copy_user_payload(int user_len, char *src) {
    char safe_buf[64];

    // Developer checks upper bound, forgetting user_len can be NEGATIVE!
    if (user_len > 64) {
        return -1; // If attacker sends user_len = -5, (-5 > 64) is FALSE! Check passes!
    }

    // Now signed -5 (0xFFFFFFFFFFFFFFFB) is passed as unsigned size_t:
    // (size_t)(-5) == 18,446,744,073,709,551,611 bytes!
    memcpy(safe_buf, src, user_len); // Instant stack overflow / crash!
    return 0;
}
Extra C Trap — Comparing Signed and Unsigned Directly:
What does if (-5 > sizeof(safe_buf)) evaluate to in C? Because sizeof() returns an unsigned size_t, C's Usual Arithmetic Conversion rule silently converts -5 to unsigned 18446744073709551611 BEFORE comparing! So (-5 > 64U) evaluates to TRUE! Never mix signed int and unsigned size_t without checking len < 0 first.

Vulnerability Class 3: Signed Overflow Undefined Behavior (Compiler Betrayal!)

In the C standard, unsigned overflow is guaranteed to wrap modulo $2^N$. However, signed integer overflow is Undefined Behavior (UB). That means optimizing compilers (gcc -O2, clang -O2) are legally allowed to assume signed overflow never happens in your program: 

/* BROKEN check on signed int — DO NOT WRITE THIS! */
int a = get_user_int(); // positive int
if (a + 100 < a) {     // gcc -O2 says: "In math, a+100 is NEVER < a. Delete this if-block!"
    return -1;          // This entire security check disappears from the compiled ELF binary!
}

/* CORRECT, Bulletproof Ways to Check Overflow in C: */
uint32_t total = 0;
if (__builtin_add_overflow(u_len, 100, &total)) { return -1; } // Method 1: Compiler intrinsic (best!)
if (u_len > UINT32_MAX - 100) { return -1; }                  // Method 2: Safe subtraction pre-check

Section 0.1.6 • Why RAM Looks "Backwards" in GDB

6. Endianness: Little-Endian (x86_64/ARM64) vs. Big-Endian (Network)

Suppose you declare uint32_t magic = 0x12345678; in C. That 32-bit integer occupies 4 consecutive bytes in RAM: 0x12 (Most Significant Byte, MSB), 0x34, 0x56, and 0x78 (Least Significant Byte, LSB). In what order should the CPU place those 4 bytes into memory addresses 0x1000, 0x1001, 0x1002, and 0x1003?

  • Little-Endian (Intel/AMD x86_64 & ARM64 Linux): "Little End First!" The Least Significant Byte (0x78) goes into the lowest memory address (0x1000), and the Most Significant Byte (0x12) goes into the highest address (0x1003).
  • Big-Endian (TCP/IP Network Packet Headers): "Big End First!" The Most Significant Byte (0x12) goes into the lowest memory address (0x1000), matching left-to-right human writing.
Figure 2: Little-Endian reverses multi-byte integers byte-by-byte in RAM, while 1-byte char arrays stay sequential.
2 Common Beginner Misconceptions About Little-Endian (Clear Them Up Right Now!):
  1. "Why is it 78 56 34 12 and NOT 87 65 43 21?" — Because memory is addressed by byte (2 hex digits), never by nibble! Inside each single byte (0x78), the two hex digits never swap.
  2. "Why doesn't the string "HELLO" get stored backwards as "OLLEH"?" — Because a string is an array of separate 1-byte char elements (s[0]='H', s[1]='E', ...). Endianness only affects single multi-byte numbers (like uint16_t, uint32_t, uint64_t, and 64-bit pointers).
Section 0.1.7 • LangSec & Real Historical Parser CVEs

7. Character Encoding, Null-Byte (0x00) Truncation & UTF-8 Traps

How does a program know where a text string ends? There are two fundamentally incompatible designs used across software:

  1. Length-Prefixed / Buffer Strings (Python, Go, Rust, Java, HTTP bodies, ASN.1 certificates): Store an explicit length (e.g., len = 15) alongside the byte array. A 0x00 byte in the middle is treated as just another normal character!
  2. NUL-Terminated C Strings (char * in C, Linux syscalls like open(), strcmp(), strlen()): Store NO length! They read byte-by-byte from the start pointer and stop immediately at the very first 0x00 ('\0') byte.
Figure 3: When a length-aware validator guards a C-string sink, an embedded 0x00 byte splits perception in two.

2 Famous Real-World Disasters Caused by Encoding Differentials

  • Case Study 1 — The Universal SSL/TLS Certificate Null-Byte Hack (Moxie Marlinspike, Black Hat 2009): X.509 SSL certificates store domain names using ASN.1 length-prefixed strings. Researchers requested a legitimate certificate for the domain www.paypal.com\x00.thoughtcrime.org. The Certificate Authority's length-aware parser saw a subdomain belonging to thoughtcrime.org and signed it! When web browsers (written in C/C++) verified the certificate, their C string comparison stopped at \x00 and saw www.paypal.com—granting a valid PayPal HTTPS padlock to an attacker!
  • Case Study 2 — UTF-8 Overlong Slash Path Traversal (%c0%af IIS CVE-2000-0884): Standard ASCII / is 1 byte: 0x2F (0010 1111). UTF-8 allows multi-byte characters (110xxxxx 10xxxxxx). Attackers encoded / illegally across 2 bytes as 0xC0 0xAF. The security filter checked for ../ (0x2E 0x2E 0x2F), saw no 0x2F, and let it pass. Then a non-strict UTF-8 decoder translated 0xC0 0xAF back into / and let attackers read arbitrary files on the server!
Attacker Checklist at Every Input Boundary

Test boundary integers (0, -1, INT32_MIN, UINT32_MAX), numbers that wrap when multiplied by struct sizes, embedded \x00 bytes, and multi-byte UTF-8 tricks to see if two components parse the same bytes differently.

Defender Golden Rules

1. Use __builtin_add_overflow / __builtin_mul_overflow.
2. Reject len < 0 explicitly before casting to size_t.
3. Reject embedded NUL bytes (memchr(buf, '\0', len) != NULL).
4. Canonicalize/decode UTF-8 strictly before running security filters.
