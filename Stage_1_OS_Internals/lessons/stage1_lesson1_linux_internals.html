Module 1.1 • Execution Model

1. Linux Boot, Process Hierarchy & the /proc Virtual Filesystem

In Linux, almost everything runs either in Kernel Space (hardware access, memory, scheduling, security checks) or User Space (isolated processes making system calls into the kernel).

  • Boot Chain: Firmware (UEFI) → Bootloader (GRUB2) → Kernel (vmlinuz) + initramfs → mounts root filesystem → spawns PID 1 (systemd on a host OS, or your container's entrypoint inside Docker).
  • fork() + execve(): Processes spawn children by cloning their kernel descriptor (task_struct, giving a child its own PID and linking its PPID to the parent), then calling execve() to load the target ELF binary into memory.
  • /proc (procfs): Not stored on disk (0 bytes)! It is a live window into kernel memory. Every running process <PID> has a folder /proc/<PID>/.
Figure 1: Process spawning via fork()+execve(), kernel security enforcement, and live inspection via /proc.
# Inspect your current shell's process tree, credentials, and capabilities
ps -eo pid,ppid,user,ruid,euid,comm --forest
ls -la /proc/$$/
grep -E '^(Name|Pid|PPid|Uid|Gid|Cap)' /proc/$$/status
tr '\0' ' ' < /proc/$$/cmdline; echo
Attacker Lens

Enumerates ps aux and /proc/*/environ or cmdline looking for plaintext passwords, API tokens, or root processes spawning subshells with unsafe environment variables.

Defender / Forensic Lens

Uses ls -la /proc/*/exe | grep deleted to spot fileless/deleted malware still executing in RAM, and audits unexpected PPID → PID chains (e.g., nginx spawning /bin/sh).

Module 1.2 • Discretionary Access Control

2. DAC Permissions, Directory Semantics & Interactive Octal Calculator

Standard Linux permissions (DAC) assign three rights—Read (r=4), Write (w=2), and Execute (x=1)—across three identities: Owner (u), Group (g), and Others (o).

Permission Meaning on a Regular File Meaning on a Directory (Common Security Trap!)
r (4) Read file contents. List filenames inside (ls), without metadata unless x is also set.
w (2) Modify or truncate file contents. Create, rename, or delete files inside — even if you don't own those files (unless Sticky Bit is set!).
x (1) Execute as a program / script. Traverse (cd) into the directory and access file inodes inside.

umask: Masks off permissions when creating new files. Files start with max 0666 (never executable by default), directories with 0777. A default umask 0022 produces 0644 files (rw-r--r--) and 0755 directories (rwxr-xr-x). Security-sensitive files/keys should use umask 0077 (0600 / 0700).

Module 1.3 • Privilege Transitions

3. Special Bits: SUID (4000), SGID (2000) & Sticky Bit (1000)

Every running process carries multiple UIDs in the kernel. The two most important for privilege escalation are:

  • Real UID (RUID): Who launched the process (e.g., student, UID 1000).
  • Effective UID (EUID): Whose permissions the kernel actually checks when accessing files or syscalls!

Normally, RUID == EUID. When you run a SUID binary owned by root (such as /usr/bin/passwd), the kernel keeps RUID = 1000, sets EUID = 0, and lets that binary temporarily edit /etc/shadow safely.

Figure 2: How SUID elevates EUID to the file owner, and why Debian/Ubuntu /bin/sh requires -p to preserve EUID.
Key Kernel & Shell Rules to Remember:
  • No SUID on Shebang Scripts: Linux ignores SUID/SGID bits on interpreted scripts starting with #! (e.g. #!/bin/bash) to prevent Time-of-Check-to-Time-of-Use (TOCTOU) race attacks. Only ELF binaries obey SUID.
  • dash / bash EUID Drop: On Ubuntu, /bin/sh (dash) detects EUID != RUID and silently drops privileges back to RUID unless invoked with -p (privileged mode)!
  • SGID (2000) & Sticky (1000): SGID on directories forces new files to inherit the directory's group. Sticky bit on /tmp (1777) stops users from deleting other users' temp files.
Module 1.4 • Fine-Grained Privileges

4. Linux POSIX Capabilities: Beyond All-or-Nothing Root

Historically, if a tool like ping needed to open a raw ICMP socket, admins had to make it SUID root—handing over full god-mode root access just for one network syscall. Linux Capabilities break root into 40+ discrete privileges stored in a file's extended attributes (security.capability), not in chmod permission bits!

Figure 3: Splitting monolithic root into discrete capabilities—and why some capabilities still equal full root.
Capability Intended Purpose Security Impact If Misconfigured on Tool/Interpreter
cap_net_bind_service Bind privileged ports (< 1024) like 80/443 without root. Low direct escalation risk; good least-privilege practice for web servers.
cap_net_raw Open raw/packet sockets (ping, tcpdump). Allows packet sniffing / ARP/ICMP spoofing on the attached network segment.
cap_dac_read_search Bypass file read & directory read/search permission checks. Critical Confidentiality Breach: Lets any user read /etc/shadow, SSH private keys, or root files! (Note: dropped from Docker's default bounding set.)
cap_dac_override Bypass file read, write, AND execute DAC permission checks. Critical Read/Write Breach: Lets a binary read /etc/shadow OR overwrite root-owned files (and is active in Docker's default bounding set!).
cap_setuid Allow a process to arbitrarily set its own UID (setuid(0)). Instant Full Root: On Python/Perl/Node/custom binary, one syscall grants UID=0 root shell!
cap_sys_admin Mount filesystems, namespaces, BPF, trace/admin tasks. Equivalent to Full Root: Can mount host/cgroups or escape containers.
Important Blind Spot: A file with cap_setuid+ep shows completely normal permissions (-rwxr-xr-x) in ls -la and will NOT show up in find / -perm -4000. Always audit BOTH SUID/SGID (find) AND Capabilities (getcap -r / 2>/dev/null)! Also note: +ep means Effective and Permitted (active immediately upon execution).
Module 1.5 • Command-Line Security Triage

5. Essential Security Triage Commands

Memorize these manual enumeration & verification commands before writing Python automation in Step 4:

# 1. Find all SUID (4000) or SGID (2000) binaries cleanly
find / -perm -4000 -type f 2>/dev/null
find / -perm /6000 -type f -exec ls -la {} + 2>/dev/null

# 2. Find all binaries carrying Linux File Capabilities
getcap -r / 2>/dev/null

# 3. Check for rogue UID 0 users in /etc/passwd
awk -F: '$3 == 0 {print $1, $3, $7}' /etc/passwd

# 4. Find world-writable directories missing the Sticky Bit (1000)
find / -xdev -type d \( -perm -0002 -a ! -perm -1000 \) 2>/dev/null

# 5. Decode process effective capabilities from /proc/self/status
grep CapEff /proc/self/status
capsh --decode=0000000000000000
